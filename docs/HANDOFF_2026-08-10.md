## What shipped (this agent)

### 1. Image display-resolution strategy (the through-line)
Renders are native 4K PNGs (20–40 MB); the app showed them everywhere at a
fraction of that size, pulling the full file each time.
- **Seed fix** `d6cc4e1` — takes strip served a 512px thumbnail instead of the 4K PNG.
- **Full strategy** `0c81579` — `app/imaging.py`: display tiers `thumb`≤512 /
  `md`≤1600 (WebP) / `full` (source), one `variant_path` builder (lazy,
  mtime-guarded, never upscales, falls back to source). `?size=` on the image
  endpoints; every display site mapped to a tier; lightbox/crop/repair stay full.
- **Storefront** `71a26be` — `scripts/build_images.py` + `srcset` responsive
  WebP; landing page ~92 MB → ~0.4 MB. Docs: `docs/IMAGE_SERVING.md`.
- **Review focus:** the tier map in `app.js` (any site still pulling `full`
  needlessly?), and `imaging.VARIANTS` sizes vs 2× DPR.

### 2. Generation reliability — the image regression + the 502 (incident)
Three linked fixes, root-caused live with the user:
- `6fb76e0` — the tiered work had **no cached WebP for the back-catalogue**, so a
  cold board fired dozens of synchronous 4K decode→resize builds at once,
  saturating a small tenant (slow everything + stalled the lightbox). Fix: a
  build **semaphore** (bounded concurrency, double-checked), a **boot pre-warm**
  sweep (`generate.warm_all_candidates` / `store.warm_all_references` in a
  background thread at startup), and an **md-first lightbox** (full only on 100%
  zoom).
- `d92229a` — the eager variant-warm I'd added **inside the render request** was a
  second 4K decode on top of the render's own memory; removed from all
  render/assembly paths (lazy + boot-warm cover it). Reduces OOM risk.
- `d4dc92b` — **the actual 502 root cause**: the render *completes* but a gateway
  times out the long synchronous request (~1 min) and returns "Application failed
  to respond"; the flight recorder never sees it. Fix: `api()` tags gateway
  errors; `runGenerate` snapshots existing takes and, on a gateway cut,
  **polls `/candidates` for the new take** instead of showing a failure
  (`pollForNewTake`). Real app errors still report immediately.
- **Review focus:** this last fix is a **client-side workaround**. The durable
  fix — **fire-and-poll async generation** with render-outcome logged to the
  Status panel — is an agreed but **unbuilt follow-up** (also closes the original
  "a 502 leaves no status-panel entry" complaint). Also: the tenants are small
  Railway instances and 4K renders are memory-heavy — consider bumping tenant
  memory in the provisioner.

### 3. Camera & composition language
`6a7314c` (initial) + backend folded into the concurrent commits + `a8ec033`
(revision frontend). Structured per-panel axes — `camera_angle`, `camera_lens`
(a focal length; presets + **Custom**), `camera_tilt`, `scale` (adds
Aerial/Macro/Micro) — each resolved `panel → production default → unset`. The
default is baseline-merged (`CAMERA_BASELINE` = Eye level · 24mm · Level · Wide)
and edited on the **Camera grammar bar at the top of the Look Interview**.
`generate._camera_block` expands each axis into an authored directive placed after
PANEL PURPOSE and stated to **override the references' framing** (the old fix for
"High Camera Angle" being ignored). Per-panel edits between takes via
`store.amend_panel_camera` (lock re-stamp/journal/frozen). Full ref:
`docs/CAMERA_AND_COMPOSITION.md`. **Review focus:** legacy lens migration
(`_LEGACY_LENS`), and the three UI surfaces (`docs/CAMERA_AND_COMPOSITION.md` table).
